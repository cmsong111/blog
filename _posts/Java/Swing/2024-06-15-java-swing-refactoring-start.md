> 2학년 2학기 Java 수업에서 만든 Swing 음식점 정보 조회 프로그램을 다시 열어 보고, 코드의 문제점과 앞으로 진행할 리팩토링 계획을 정리합니다.

## 프로젝트 소개

이 프로젝트는 2학년 2학기 Java 수업 과제로 개발한 **Java Swing 기반 음식점 정보 조회 프로그램**입니다.

당시 스프링 부트를 공부하던 중이었기 때문에, 화면만 Swing으로 만들지 않고 별도의 백엔드 서버를 구축해 HTTP로 연동하는 구조를 선택했습니다. 수업 과제로는 다소 욕심을 낸 구성이었지만, 덕분에 클라이언트와 서버를 나눠 설계하는 경험을 처음 해볼 수 있었습니다.

- [음식점 정보 시스템 프로젝트 - 프론트(Swing)](https://github.com/cmsong111/Restaurant-information-system/tree/main)
- [음식점 정보 시스템 프로젝트 - 백엔드(참고)](https://github.com/cmsong111/Restaurant-information-system-server/tree/main)

시간이 지나 다시 코드를 열어 보니, 당시에는 동작하는 것만으로 만족했던 부분들이 눈에 많이 걸렸습니다. 그래서 이 프로젝트를 리팩토링 연습 대상으로 삼아 단계적으로 개선해 보기로 했습니다.

## 프로젝트 코드 진단

코드를 다시 읽으며 발견한 문제를 다섯 가지로 정리했습니다.

| 번호 | 문제 | 영향 |
| :--- | :--- | :--- |
| 1 | 패키지 구조 부재 | 역할별 코드 위치를 찾기 어려움 |
| 2 | Apache HttpClient 보일러플레이트 | 요청마다 비슷한 코드가 반복됨 |
| 3 | 화면 클래스의 `static` 전역 상태 | 데이터 흐름 추적과 테스트가 어려움 |
| 4 | 리소스 직접 로드 | 폰트 등 리소스 로딩 코드가 흩어짐 |
| 5 | `System.out` 기반 출력 | 로그 레벨 구분과 파일 기록이 불가능 |

### 1. 패키지 구조가 없습니다

패키지가 `DTO`, `PAGE`, `HTTP` 세 가지로만 나뉘어 있고, 이름도 대문자로 시작합니다. Java 패키지 명명 관례(소문자)에 맞지 않을 뿐 아니라, 화면·통신·모델의 경계가 명확하지 않아 클래스가 늘어날수록 위치를 찾기 어려워집니다.

### 2. HTTP 통신 코드에 보일러플레이트가 많습니다

Apache HttpClient로 직접 요청을 만들고, 응답 JSON을 Gson으로 변환하는 코드가 API마다 반복됩니다. 요청 생성, 예외 처리, 역직렬화가 한 메서드 안에 섞여 있어 새로운 API를 추가할 때마다 비슷한 코드를 복사하게 됩니다.

### 3. 화면 클래스가 데이터를 static으로 보관합니다

`HomePage`, `DetailPage` 클래스가 조회한 데이터를 `static` 필드에 담아 전역으로 공유합니다. 어느 화면에서든 값을 바꿀 수 있기 때문에 데이터가 언제 어디서 변경되는지 추적하기 어렵고, 객체지향적인 설계와도 거리가 멉니다. 안드로이드 등 다른 UI 프레임워크의 상태 관리 방식을 참고해 개선할 계획입니다.

### 4. 리소스를 직접 로드합니다

폰트 같은 리소스를 필요한 곳에서 직접 읽어 오는 코드가 여러 곳에 흩어져 있습니다. 리소스를 한곳에서 관리하는 방법을 찾아 디자인 패턴으로 정리해 보려 합니다.

### 5. 로그를 단순 출력으로 남깁니다

디버깅 정보를 `System.out.println`으로 출력하고 있어 로그 레벨을 구분하거나 파일로 남길 수 없습니다. 로깅 라이브러리를 도입하는 것이 가장 먼저 손댈 수 있는 개선점이라고 판단했습니다.

## 리팩토링 계획

진단 결과를 바탕으로 아래 순서로 리팩토링을 진행할 예정입니다.

1. **프로젝트 아키텍처 재설계**: 역할 기준으로 패키지를 다시 나누고 소문자 명명 규칙을 적용합니다.
2. **MVC 패턴 적용**: 화면(View)과 데이터·로직을 분리해 `static` 전역 상태를 제거합니다.
3. **Java에서 Kotlin으로 전환**: Kotlin으로 옮기면서 Lombok 의존성도 제거합니다.
4. **Retrofit2 도입**: 인터페이스 선언만으로 HTTP API를 정의해 통신 보일러플레이트를 줄입니다.
5. **비동기 처리 적용**: 네트워크 요청이 UI 스레드를 막지 않도록 리액티브 방식이나 Coroutine을 검토합니다.

여기에 더해, 진단 5번의 로깅 문제는 비교적 작은 변경으로 해결할 수 있어 첫 작업으로 먼저 진행합니다. 실제 적용 과정은 [Java Swing 프로젝트에 SLF4J와 Logback 도입하기](/posts/java-swing-refactoring-logging/)와 [Swing에 Retrofit2 적용하기](/posts/java-swing-refactoring-retrofit2/)에 정리했습니다.

## 정리

수업 과제로 만든 코드를 다시 보는 일은 조금 부끄럽지만, 무엇이 왜 문제인지 직접 설명해 보는 좋은 연습이 됩니다. 리팩토링을 진행하면서 아래 항목을 기준으로 점검하려고 합니다.

- [ ] 패키지가 역할 기준으로 나뉘고 명명 관례를 지키는가?
- [ ] 화면 클래스에서 `static` 전역 상태가 제거되었는가?
- [ ] 새로운 API를 추가할 때 반복 코드 없이 선언만으로 끝나는가?
- [ ] 로그 레벨을 구분해 콘솔과 파일에 남길 수 있는가?
