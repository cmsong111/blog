## 2. 어조 및 문체 규칙 (Tone & Voice)

### 2.1 기본 어미 (경어체 통일)
- 기본적으로 단정하고 차분한 **'~합니다 / ~습니다 / ~됩니다'** 경어체를 사용합니다.
  - ⭕ `"스프링 부트 환경에서 Ollama 모델을 연동하는 방법을 소개합니다."`
  - ⭕ `"이런 한계를 해결하기 위해 라이브러리를 도입해 보았습니다."`
  - ❌ `"스프링 부트에서 Ollama를 써봤는데 완전 편하더라구요 ㅋㅋㅋ"` (과도한 구어체/이모티콘 지양)
  - ❌ `"스프링 부트 환경에서 모델을 연동한다."` (일기식 평어 지양)

### 2.2 1인칭 호칭
- 1인칭 주어는 **'저'**를 사용하거나, 문맥상 자연스럽다면 **주어를 생략**합니다.
  - ⭕ `"제가 개발 편의를 위해 주로 사용하는 방식은 다음과 같습니다."`
  - ❌ `"필자는...", "본 작성자는..."` (딱딱하고 거리감이 느껴지는 표현 지양)

### 2.3 문장 호흡 및 표현
- 문장은 한 문장에 하나의 메시지만 담도록 **간결하고 명확하게** 끊어 씁니다.
- 글의 서두에는 항상 **인용구(`> ...`)를 사용해 "이 글에서 무엇을 다루는지" 1~2문장으로 명확히 요약**하고 시작합니다.
- 중요한 주의사항이나 팁은 Chirpy 콜아웃 문법을 적극 활용합니다:
  ```markdown
  > 본 문서는 Spring Boot 4.x / Java 21 환경을 기준으로 작성되었습니다.
  {: .prompt-info }

  > 주의: 해당 설정 누락 시 500 에러가 발생할 수 있습니다.
  {: .prompt-warning }
  ```

### 2.4 제목 작성 원칙 (담백하고 정제된 엔지니어링 스타일)
- 블로그 포스트 제목은 유튜브나 벨로그식 어그로/광고성 문구를 엄격히 배제하고, **담백하고 깔끔한 기술 문서 스타일**로 작성합니다.
- ❌ **금지 표현 (광고글/어그로성 문구 및 과도한 부제 지양)**:
  - 의문형/호기심 유발형: `~할 때?`, `~죽는 이유`, `~응답이 없다?`, `~의 함정`
  - 과장된 수식어: `~의 모든 것`, `완벽 해결`, `완전 정복`, `초고속`, `원클릭`, `결정적 차이`, `치명적 위험`
  - 구호형/선동형: `모든 개발자가 ~할 필요는 없다`, `~의 비밀`
  - 불필요한 콜론(`:`) 부제 나열: `주제: 부제1과 부제2`처럼 콜론 뒤에 장황한 부제를 붙이지 않고 한 문장으로 간결하게 작성합니다.
- ⭕ **권장 표현 (담백하고 명확한 엔지니어링 스타일)**:
  - 핵심 기술 키워드와 적용 대상 및 동작/해결 목적을 직관적이고 군더더기 없이 명시합니다.
  - 예: `Docker 멀티스테이지 빌드를 활용한 Spring Boot 이미지 최적화`
  - 예: `Docker 컨테이너 PID 1 프로세스와 Graceful Shutdown 설정`
  - 예: `netshoot 컨테이너를 활용한 Docker 네트워크 패킷 분석 및 디버깅`

## 3. 포스트 구성 템플릿 (2가지 표준 스타일)

글의 성격에 따라 아래 **스타일 1(문제 해결형)** 또는 **스타일 2(튜토리얼형)** 중 하나를 선택하여 작성합니다.

### 스타일 1: 문제 해결 / 트러블슈팅형 (Troubleshooting)
> 실무나 개발 중 특정 에러(500, 인증 실패 등)나 한계에 부딪혀 이를 해결한 과정을 다룰 때 사용합니다.

1. **서두 요약 (`> ...`)**: 직면했던 문제와 최종 해결책을 1~2문장으로 요약
2. **배경 및 문제 상황 (`## 문제 상황`)**: 구현 목표와 실제 발생한 에러 로그·비정상 동작
3. **원인 분석 (`## 원인 분석`)**: 내부 동작 원리나 프레임워크 스펙 관점의 근본 원인
4. **해결 방법 및 코드 (`## 해결 방법`)**: 수정된 설정 및 복붙 가능한 핵심 코드
5. **결과 검증 (`## 결과 확인`)**: 수정 전후 비교 수치, 테스트 통과 로그, 정상 동작 화면
6. **마무리 / 참고 링크 (`## 마치며` or `## 참고 자료`)**: 운영 시 주의점 및 공식 문서 링크

### 스타일 2: Quick Start / 튜토리얼형 (Tutorial)
> 새로운 기술이나 표준 스펙, 신규 플러그인을 처음 도입하고 사용하는 가이드를 작성할 때 사용합니다.

1. **서두 요약 (`> ...`)**: 이 기술/도구를 소개하는 이유와 기대 효과
2. **배경 및 트레이드오프 (`## 도입 배경`)**: 왜 필요한지, 대안과 비교해 어떤 장단점이 있는지
3. **의존성 및 설정 (`## 프로젝트 설정`)**: 기준 버전, `build.gradle.kts`, `application.yml`
4. **단계별 핵심 구현 (`## Step 1...`, `## Step 2...`)**: 내부 동작 흐름과 복붙 가능한 최소 재현 코드
5. **실행 및 동작 검증 (`## 실행 결과`)**: API 호출(`curl`), 단위 테스트(JUnit 5), 실행 로그
6. **실무 적용 시 주의사항 / 마무리 (`## 정리`)**: 운영 함정(Edge Case) 및 참고 링크

## 4. 코드 스니펫 작성 원칙 (Code Guidelines)

1. **즉시 복사/붙여넣기(Copy & Paste) 가능한 완성도**: 생략 부호(`...`) 남발을 피하고 필요한 어노테이션과 주요 import·의존성을 명시합니다.
2. **언어 식별자 필수 지정**: `kotlin`, `java`, `bash`, `yaml`, `json` 등을 블록 시작부에 명시합니다.
3. **파일명/클래스 역할 주석**: 파일 상단에 주석으로 경로를 표기해 독자가 위치를 직관적으로 파악할 수 있게 합니다.
4. **Kotlin First (주제에 맞게 유연 적용)**: 백엔드 애플리케이션 코드는 특별한 이유가 없는 한 Kotlin을 기본으로 하되, Java 표준 스펙 등 Java가 자연스러운 주제는 Java로 작성합니다.

## 5. 이미지 및 스크린샷 규칙 (Visuals)

1. **저장 위치**: `assets/images/YYYY-MM-DD/`에 로컬 저장합니다(프로덕션 jsDelivr CDN 자동 적용).
2. **코드 이미지 캡처 금지**: 코드·설정·명령어는 반드시 마크다운 코드 블록으로 작성합니다.
3. **빈 박스 및 미로딩 이미지 방지**: 완전히 로딩된 화면만 캡처합니다.
4. **타이트 크롭 (Tight Crop)**: 불필요한 여백을 잘라내고 핵심 UI 영역만 선명하게 담습니다.
5. **보안 마스킹**: API 키(`AIza...`, `sk-...`, 토큰 등)와 개인정보는 이미지에서 반드시 마스킹하고 코드에도 환경 변수로 표기합니다.
6. **대체 텍스트 & 링크 프리뷰**: 이미지에는 의미 있는 `alt`를 작성하고, 외부 링크는 `{% linkpreview "URL" %}` 태그를 활용합니다.
7. **Aside 브라우저(`aside` MCP) 우선 활용**: 공식 문서 확인과 로그인 세션이 필요한 화면 캡처 시 적극 활용합니다.

## 9. 상세 기술 블로그 집필 심화 체크리스트

단순 사용법 요약을 넘어 실무 개발자가 북마크하는 밀도 높은 글을 쓰기 위해 아래 6가지를 점검합니다.

- [ ] **`Why`와 `Trade-off` 명시**: "어떻게 쓰는가"보다 "왜 이 대안을 선택했는지", "언제 쓰면 안 되는지(한계·안티패턴)"가 최소 1문단 이상 포함되었는가?
- [ ] **내부 동작 원리 한 단계 더 파기 (One Layer Deeper)**: 어노테이션·설정 뒤에서 동작하는 핵심 클래스(`BeanPostProcessor`, `FilterChain`, `HandlerMethodArgumentResolver` 등)와 실행 순서를 짚어주었는가?
- [ ] **실패 로그와 검증 결과 포함**: 트러블슈팅 글이라면 실제 에러 로그(핵심 3~5줄), 원인 가설, 수정 전/후 수치(응답 시간·이미지 크기·테스트 통과 로그)를 남겼는가?
- [ ] **운영 함정(Edge Case) 정리**: 해피 패스 외에 프로덕션에서 자주 터지는 주의사항(프록시 내부 호출, 타임아웃, 메모리/커넥션 누수, 호환성 이슈 등)을 1가지 이상 짚었는가?
- [ ] **표와 다이어그램으로 정보 압축 (모바일 가독성 고려)**: A vs B 비교는 Markdown 표로 정리하고, Mermaid는 꼭 필요한 핵심 흐름만 **`flowchart TD`(세로 방향) · 4~6개 노드 / 참여자 3~4개 이내**로 간결하게 구성해 모바일에서 가로 축소로 글자가 작아지지 않게 했는가?
- [ ] **기준 버전과 실행 증거 명시**: 글 상단에 기준 환경/버전을 명시하고, 독자가 그대로 따라 해 검증할 수 있는 최소 재현 예제(`build.gradle.kts` + 코드 + `curl`/테스트)를 제공했는가?
